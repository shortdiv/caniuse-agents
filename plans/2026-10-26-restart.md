# Restart: caniuse for coding-agent harnesses

Status: draft for review · 2026-10-26

## Goal

A caniuse-style reference for the harnesses people actually build on. It answers two questions per harness and version:
1. **Can I use X?** Capabilities: hooks, MCP, tools, instructions, memory.
2. **What does X write?** Its session log format, and how that changed between versions.

The second one is new. It's a living reference for anyone parsing agent sessions, including Tallygent, whose parsers will run against its fixtures as tests.

## What stays

- **The design:** IBM Plex, the existing colour tokens in `src/styles/global.css`, light and dark themes, the header and footer, and the `CiuTable` version grid. New pages reuse these. No redesign.
- **The data layout:**

  - `data/agents/*.json` (support codes per version);
  - `data/features/*.json` (feature definitions);

- **Feature pages** (`/features/[featureId]`) and the index.

## Models

**Models are not an axis of the grid.** Capabilities and log formats belong to the harness, and every harness version runs several models. Instead:
- **Per version:** keep `models` on each version in `agents.json`, as the models available or default at that version. Show them on the harness page, not in the grid.
- **Model-gated features:** a few features depend on the model, e.g. computer use, image input, reasoning levels, large context windows, fast modes. They get a `requires: "model"` flag and a note naming which models support them.
- **Formats ignore models entirely.** The model is just a field in the log.

## New: log formats

```
data/formats/<harness>.json        what the harness writes, by format generation
fixtures/<harness>/<generation>/   synthetic log lines (no real text) + the expected parse
```

**Format generations, not eras.** `era` already means the grid's time column in `agents.json`, so log-format versions are called **generations**. Each generation records:
- **Range:** `since` and `until`, as harness versions that exist in `agents.json`;
- **Where:** where logs live, and the container (JSONL or a JSON document);
- **How to recognize it,** from the log itself.

  This matters because datasets like SWE-chat don't record the harness version, so the log's shape is the only clue.
- **Signals:** for each of the following, where it's logged and at what granularity:
  - prompt, injected context;
  - tool call, failure, decline, interrupt;
  - compaction, subagent;
  - model, tokens (cumulative or per message).
- **Quirks.**
- **Sources,** each fact marked `docs` or `source`.

**Observed facts stay local.** Anything learned only from your own logs is not published. It goes in a gitignored `local/` notes folder until docs or source code confirm it.

**Seed facts already known:**
- **Codex** has at least three generations: `function_call`/`exec_command`; `custom_tool_call` with `exec_command_end`; `item_completed`. SWE-chat mixes all three.
- **Claude Code** before 2.1.97 logged placeholder token usage on the first line of a message. That's confirmed in a SWE-chat sample.
- **OpenCode 1.2.0** moved from JSON files to SQLite.
- **Pi** logs a tree of entries with a version header.

Each needs a source before it goes in.

**The pages:**
- `/formats`: an index of harnesses.
- `/formats/<harness>`: its generations, the table of signals, and a changelog of format changes.

Same components and styling as the feature pages.
